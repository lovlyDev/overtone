# ТЗ: доделать Overtone (мод для десктопной Яндекс Музыки)

Ты продолжаешь проект на середине. Сначала прочитай этот файл целиком, потом код. Всё общение с пользователем и комментарии в коде — на русском.

## 1. Что это

Overtone — мод для десктопной Яндекс Музыки (Windows, Electron 38.2.2, приложение 5.127.0). Патчер дописывает в `app.asar` маленький загрузчик, весь остальной код живёт снаружи и грузится при запуске.

Цели пользователя по приоритету:

1. **SoundCloud как родная часть приложения.** Поиск по SoundCloud открывает обычную страницу плейлиста приложения; треки играют в родном плеере (с меткой «SoundCloud»), очередь, перемотка, «следующий» работают как у треков Яндекса; сердечко добавляет трек SoundCloud в «Мне нравится», где он стоит по дате вперемешку с родными. Никаких самописных оверлеев поверх интерфейса.
2. **Скорость.** Поиск и старт трека быстрые; треки грузятся порциями по мере прокрутки, а не все сразу.
3. Темы, стекло, видео трека — уже есть, только поддерживать.

## 2. Как запускать и проверять

Код мода грузится прямо из папки проекта (режим `--dev`, путь лежит в `%APPDATA%\Overtone\dev-path.txt`), поэтому правка файла + перезапуск приложения = проверка. Переустанавливать патчер не нужно.

| Команда | Что делает |
|---|---|
| `node tools/check.js` | синтаксис всех файлов + пробный патч архива на копии |
| `node patcher/cli.js status` | установлен ли мод, совпадает ли хеш архива с exe |
| `powershell -ExecutionPolicy Bypass -File tools/restart.ps1` | перезапуск приложения с отладочным портом 9333, ждёт готовности страницы |
| `node tools/eval.js "<js>"` | выполнить JS в странице приложения, вывести результат |
| `node tools/eval.js --shot файл.png` | скриншот страницы |
| `node tools/console.js <сек> "<js>"` | собрать ошибки консоли страницы |
| `node tools/sniff.js <сек> файл.json "<js>"` | записать запросы приложения к API (без заголовков авторизации) |

Журнал перехватчика: `%APPDATA%\Overtone\api.log` (пишется, пока в `config.json` стоит `"debug": true`).

**Пользователь сидит в этом же приложении.** Перед каждым перезапуском предупреждай его одной строкой. Не кликай по его интерфейсу без нужды.

## 4. Идея SoundCloud (уже частично написана в core/api.js)

Трек SoundCloud получает номер `7_000_000_000_000 + scId` (13 цифр, начинается с `70`). У Яндекса таких номеров нет.

- Поиск: `soundcloud.search()` → yt-dlp `scsearch30:` → запись в реестр → ключ из 12 hex-знаков. Страница открывается как `/playlists?playlistUuid=50c10ad0-0000-4000-8000-<ключ>` (приложение принимает только UUID-подобные адреса, `sc.xxx` даёт «Ничего не нашлось»).
- Перехват в `core/api.js`:
  - `GET /playlist/50c10ad0-…` → отдаём собранный плейлист (`searchPlaylist`);
  - `POST /tracks` → для наших номеров отдаём полные карточки (`richTrack`); смешанные списки дополняем на этапе ответа;
  - `GET /get-file-info[/batch]` с нашими номерами → `transport: "raw"`, `codec: "aac-mp4"`, `urls: [http://127.0.0.1:<port>/sc/<id>.m4a]`; сам файл качает yt-dlp (`hls_aac_160k`/`hls_aac_96k`);
  - `POST /users/{uid}/likes/tracks/add?track-id=…` и `/likes/tracks/{id}/remove` для наших номеров → сохраняем в `soundcloud.json`, отвечаем `{revision}`;
  - `GET /playlist/lk.*` (Мне нравится) и `/landing-blocks/collection/playlist-with-likes` → на этапе ответа подмешиваем наши лайки;
  - любые другие запросы с нашими номерами → 404, на серверы Яндекса не уходят; `/plays` с ними → `"ok"`.

Плейлист «Мне нравится» в ответе сервера содержит только `{id, albumId, timestamp, originalIndex}`; карточки приложение дозапрашивает через `POST /tracks` порциями — это и даёт подгрузку по прокрутке, свою делать не нужно.

## 5. Главный баг, с него начать

**Ответы, которые мы формируем на этапе запроса (`Fetch.fulfillRequest` в `onRequest`), приходят в страницу со статусом 0.** Тело при этом читается (проверено: `fetch` из страницы вернул `type: "cors"`, 4632 байта, `status: 0`). Приложение считает это ошибкой и показывает «Что-то пошло не так». Правка ответов на этапе Response (подмешивание лайков) работает и приходит со статусом 200.

Изменение CORS-заголовков и `responsePhrase` не помогли — CORS не причина.

Главная гипотеза: приложение в `index.js` вешает на сессию `webRequest.onHeadersReceived` и отвечает `callback({ responseHeaders })` **без `statusLine`** (функции `corsHandler`/`handleHeadersReceived`, фильтр `*://*/*`). Для ответа, созданного через CDP, у Chromium, похоже, нет исходной строки состояния, и код становится 0.

Порядок работы:

1. **Подтвердить гипотезу.** Временно перенести фальшивый плейлист на этап Response: в `onRequest` пропускать `/playlist/50c10ad0-…` дальше, добавить шаблон `${API}playlist/50c10ad0-*` с `requestStage: 'Response'`, в `onResponse` принимать любой код сервера и отвечать `fulfillRequest` с `responseCode: 200` и заголовками сервера (без `content-length`/`content-encoding`). Если стало 200 и страница показала строки с `trackId=70…` — виноват этап Request.
2. **Починить по-хорошему.** В `core/main.js` внутри `app.whenReady()` (до создания окна приложения) обернуть `session.defaultSession.webRequest.onHeadersReceived` так, чтобы любой колбэк, переданный приложением, отвечал с `statusLine: details.statusLine || 'HTTP/1.1 200 OK'`, а для наших 404 — соответствующей строкой. Учти, что `onHeadersReceived` может вызываться с фильтром и без, у одного listener на сессию. После этого вернуть фальшивый плейлист на этап Request.
3. **Запасной путь**, если пункт 2 не сработает: перенести всё в этап Response (запрос уходит на сервер, ответ заменяем). Минус — лишний сетевой запрос и номера SoundCloud уходят на сервер Яндекса; тогда хотя бы не утекать им в логи: сервер на неизвестный номер ответит ошибкой, мы её заменим. Ещё запасной путь — обёртка `window.fetch` в основном мире страницы, но сначала проверь логированием, что HTTP-клиент приложения вызывает `fetch` в момент запроса, а не держит ссылку.
4. После починки проверить **каждый** перехват отдельным `fetch` из страницы через `tools/eval.js`: плейлист, `/tracks` (только наши, смешанные, частичная порция), `get-file-info` и `get-file-info/batch`, лайк и снятие лайка, «Мне нравится».

## 6. Что ещё сделать (после п. 5)

### 6.1 Воспроизведение
- Убедиться, что родной плеер играет файл с `http://127.0.0.1:<port>/sc/<id>.m4a`. Медиасервер уже отдаёт CORS-заголовки и Range. Если плеер требует `.mp4`-контейнер или другой кодек — `hls_aac_*` от yt-dlp даёт `.m4a` (AAC в MP4), подобрать `codec` в ответе `get-file-info` (`aac-mp4` / `aac`).
- Проверить перемотку, «следующий», конец трека, повтор, перемешивание.
- Родной плеер не должен падать на отсутствии `r128`, `fade`, `derivedColors`; если падает — добавить в `richTrack` нейтральные значения.
- Метка «SoundCloud»: сейчас в `richTrack` поле `version: 'SoundCloud'` (показывается серым рядом с названием). Пользователь хочет плеер «как оригинальный, только с пометкой SC». Сделать аккуратный оранжевый значок SoundCloud рядом с названием трека в плеере и в строках списков (по аналогии с `page/45-clips.js`, распознавать по `trackId=70…` в ссылке), а `version` убрать.

### 6.2 Скорость
- Старт первого трека: файл качается yt-dlp ~2–5 с. `soundcloud.search()` уже заранее качает первые 3 трека; при `get-file-info` докачивается следующий. Проверить, что это работает, и не держать запрос `get-file-info` дольше нужного — лучше сразу отдать адрес медиасервера, а он сам дождётся загрузки (сервер уже ждёт `soundcloud.file()`).
- Поиск через yt-dlp ~5–10 с: показать в окошке поиска понятное ожидание; повторный тот же запрос в течение 15 минут берётся из кеша (уже есть).
- Не качать параллельно больше 2 треков.

### 6.3 Мне нравится
- Лайк трека SoundCloud из родного сердечка → трек появляется в «Мне нравится» на своём месте по дате, счётчик в коллекции растёт; снятие лайка — наоборот. Проверить, что приложение не откатывает лайк после `collection/sync` (у сервера свой счётчик ревизий; если откатывает — подправлять ответ `collection/sync` на этапе Response).
- Сердечко должно правильно показываться заполненным для уже лайкнутых треков SoundCloud (приложение берёт состояние лайков из `collection/sync`/своего хранилища — разобраться).

### 6.4 Окошко поиска (page/60-soundcloud.js)
- Сейчас: пункт «SoundCloud» в боковой панели открывает всплывающее окошко со строкой поиска и списком прошлых запросов; Enter → переход на страницу плейлиста через `window.next.router.push`. Оставить так, но проверить, что переход срабатывает и пункт подсвечивается, пока открыта страница SoundCloud.
- Если получится — заголовок и обложка страницы: «SoundCloud: <запрос>», обложка первого трека.

### 6.5 Мелочи, о которых просил пользователь
- Панель настроек всегда закрывается кликом мимо неё (сделано, проверить в полноэкранном плеере).
- Скроллбары: тонкая полоска, под курсором толще, не вылезает за скругления (сделано для панели и меню, проверить).
- Клип в полноэкранном плеере проявляется плавно, без резкого мигания (сделано, проверить на живом клипе).

## 7. Ограничения

- **Не менять** `patcher/*` без нужды: он проверен. Не трогать `app.asar` вручную.
- **Не коммитить и не выводить** содержимое `%APPDATA%\Overtone\config.json`: там прокси пользователя с логином и паролем.
- Не обходить подписку SoundCloud Go+ и DRM; треки, которые yt-dlp не отдаёт, показывать как недоступные.
- Не тащить чужой код (ymusic_mod и др.) — только свои реализации.
- Код лёгкий: без сборщиков и зависимостей, файлы небольшие, все обращения к внутренностям приложения — в `page/10-player.js` и `core/api.js`.
- После каждого изменения: `node tools/check.js`, перезапуск, проверка через `tools/eval.js`, скриншот. Сообщать пользователю, что проверено, а что нет.

## 8. Готово, когда

1. Поиск в окошке SoundCloud открывает родную страницу плейлиста со списком треков, без «Что-то пошло не так».
2. Клик по треку играет его в родном плеере; перемотка, следующий/предыдущий, конец очереди работают.
3. Сердечко на треке SoundCloud добавляет его в «Мне нравится», после перезапуска приложения он там же.
4. Длинные списки подгружаются по мере прокрутки (видно в `tools/sniff.js` порциями `POST /tracks`).
5. В консоли страницы нет новых ошибок от наших перехватов, родные треки Яндекса работают как раньше.
